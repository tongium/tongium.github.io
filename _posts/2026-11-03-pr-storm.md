Monday morning. You open GitHub, and the notification badge says **47**.

Not 47 comments. 47 pull requests. Some from teammates, some from bots, most from teammates *using* bots. Each one is green. Each one has a tidy description. Each one says "small change, should be quick to review."

None of them are quick to review.

Welcome to the **PR storm**.

---

### What Is a PR Storm?

A PR storm is what happens when the rate of pull requests opened outruns the team's ability to actually read them.

It used to be self-limiting. Writing code was slow, so the number of PRs was roughly proportional to the number of people typing. A developer might open two or three a day. Reviewing them was work, but it was work at a human pace.

Then coding agents arrived. Now one person can kick off five agents before lunch, each one producing a branch, a diff and a pull request. A dependency bot opens twenty more. Somebody asks an agent to "fix all the lint warnings" and gets a 3,000-line PR touching 140 files.

The cost of **producing** a change dropped to near zero. The cost of **understanding** a change stayed exactly where it was.

That gap is the storm.

---

### What It Looks Like From the Inside

If you're in one, you'll recognize the symptoms:

*   **The review queue only grows.** You clear five PRs, eight new ones arrive.
*   **"LGTM" gets faster and faster.** Approvals start arriving within two minutes of a 600-line diff being opened. Nobody read it. Everybody knows nobody read it.
*   **PRs review other PRs.** An AI reviewer leaves twelve comments on an AI-written PR, the author asks an AI to address them, and the whole conversation happens without a human forming a single opinion.
*   **Merge conflicts become a lifestyle.** Ten branches touch the same config file. Whoever merges first wins; everybody else rebases, and then rebases again.
*   **Senior engineers disappear.** Not from the company. From their own work. Their whole day becomes the review queue.
*   **Bugs arrive with perfect formatting.** The code is clean, consistent, well-commented, and quietly wrong.

That last one is the dangerous part. Messy code used to be a signal. When a PR looked rushed, you slowed down and read carefully. AI-generated code always *looks* careful, so the signal is gone.

---

### Why It Happens

It's tempting to blame the tools. I don't think that's right. The storm is an incentive and process problem that the tools made visible.

1.  **We measure output, not outcomes.** If your dashboard counts PRs merged, you will get a lot of PRs merged.
2.  **Starting work is free; finishing it isn't.** Spinning up an agent takes ten seconds. Owning the result takes judgment, and judgment doesn't parallelize.
3.  **Review was always the hidden bottleneck.** We just never hit it, because writing was slower. Now the slowest step in the pipeline is a human reading a diff, and every team just discovered its true throughput.
4.  **Nobody feels responsible for the whole.** The agent wrote it, the CI passed, the reviewer approved. If it breaks, whose fault is it? It's the [Swiss Cheese Model]({% post_url 2026-05-20-views-on-fault %}) in action: agent, CI, AI reviewer and human reviewer are all slices of cheese, and each one quietly assumes the others caught the problem. That's exactly how the holes line up.

---

### The Math Nobody Wants to Do

Here's a rough back-of-the-envelope.

Say a careful review takes about 20 minutes per 200 lines. A team of six engineers, each with maybe 90 focused minutes a day to spare for review, can properly review around **5,400 lines a day** between them.

One engineer with three agents can easily produce that much before lunch.

So either review quality drops, or the queue grows forever. In practice, both happen. The queue grows *and* the reviews get shallower, because people feel guilty about the queue.

You can't out-review a machine. You have to change the shape of what reaches review.

---

### How to Weather It

Here's what I've seen work, or at least hurt less:

**1. Cap work in progress, not effort.**
Limit how many open PRs one person can have at a time. Three is a good number. If you want to open a fourth, finish or close one first. This one rule does more than any tool.

**2. Make PRs small, on purpose.**
Ask agents for one change per PR. "Rename this module" and "change this behavior" should never share a diff. A 50-line PR gets a real review. A 1,500-line PR gets a rubber stamp.

**3. The author reviews first.**
If you didn't read your agent's diff line by line, don't ask someone else to. The person who opens the PR is the first reviewer, not a courier.

**4. Write down *why*, not *what*.**
The diff already shows what changed. The description should say why this change exists, what you considered and rejected, and what the reviewer should look at most carefully. If you can't write that, you're not ready to open the PR.

**5. Batch the boring stuff.**
Dependency bumps, formatting, lint fixes: group them, schedule them, merge them on a known day with tests as the gatekeeper. Don't let them compete for human attention with real changes.

**6. Use AI reviewers as a filter, not a verdict.**
Let an AI catch the typos, the missing null checks and the obvious bugs before a human looks. But a human still owns the "should we do this at all?" question. That's the question that matters most, and it's the one machines are worst at.

**7. Measure lead time, not PR count.**
Track how long it takes for an idea to become working software in production. A storm of PRs that sit in a queue for a week is slower than a trickle that merges the same day.

---

### The Uncomfortable Bit

There's a version of this where we "solve" the storm by letting AI review AI and humans step out of the loop entirely. Merge on green. Ship it.

Maybe, for some kinds of code, that's fine. But I keep coming back to the same thought from my post on [AI slop]({% post_url 2026-10-12-ai-slop-and-dark-jokes %}): the problem was never that a machine wrote it. The problem is when **nobody checked**.

A codebase is a long conversation between the people who maintain it. Every merged PR is a sentence in that conversation. When we stop reading the sentences, we don't just risk bugs. We slowly lose the ability to explain our own system.

And one day, at 2 a.m., something breaks, and you open the file, and it's clean and well-commented and nobody on the team has ever actually read it.

That's the real cost of the storm.

---

### The Short Version

*   Writing code got cheap. Reviewing it didn't.
*   Review is now your bottleneck. Treat it like one.
*   Fewer, smaller, better-explained PRs beat more PRs.
*   The person who opens the PR owns it, whoever typed it.

The storm isn't going away. Agents are only going to get faster. The teams that do well won't be the ones that produce the most pull requests. They'll be the ones that still know what's in them.
